# 0015. Fake data and masking

**Date**: 2026-11-18
**Status**: In Progress

## Summary

This slice begins the workflow features with a fake data generator. From the Transfer section a user picks a live table, a row count, and generates deterministic, type appropriate test rows that are inserted in transactional batches. A pure domain module maps column types to fake kinds and produces values from a seeded generator, so the same seed always yields the same data and tests do not depend on randomness.

## Context

Empty or sensitive tables block development work. A native studio should let a user fill a table with believable rows in one click and keep production data out of testing. The transfer insert path, table description, and batch executor already exist, so generation is a small addition that exercises the workflow area without a new schema or driver work. Masking an existing export is recorded as a follow up rather than silently claimed.

## Requirements

**Acceptance criteria**
- **AC-1**: the Transfer section has a row count and a Generate fake rows action for the selected table.
- **AC-2**: generated values follow column types: names and emails for text columns that look like names or emails, integers, floats, booleans, uuids, timestamps, and generic text otherwise.
- **AC-3**: integer primary key columns are skipped so auto increment keys stay database generated.
- **AC-4**: the same seed produces identical rows, and different seeds produce different rows.
- **AC-5**: rows are inserted in transactional batches through the existing apply path, with an audit entry that records the table and count but never the generated values.
- **AC-6**: generation and the SQLite insert path are covered by headless tests, including the skipped key column.
- **AC-7**: the generator is verified in the container with a seeded table and a screenshot of the report.

## Decision

- **Domain**: `unidb-core::fake` owns `FakeKind`, `kind_for(type_name)`, and `generate_fake_rows(columns, rows, seed)` using a small linear congruential generator, with deterministic word lists for names and text. No new dependency.
- **Insertable columns**: columns that are primary keys with integer types are skipped, because engines generate their values. Every other column receives a generated value for its type family.
- **Values**: names and emails come from fixed pools plus the row index, integers and floats are bounded, booleans alternate from the generator, uuids are formatted from generated bytes, timestamps are RFC 3339 values in the recent past, and text uses a small word pool.
- **Execution**: the service describes the table, generates rows, builds INSERT statements with the existing dialect aware generator, and applies them in 200 row transactions. An audit entry records table, rows, and seed.
- **Interface**: the existing Transfer page gains a small fake data group with a count control, a Generate action, and the shared report line. Nothing executes outside the worker path.
- **Limits**: no masking of existing data yet, no foreign key aware values, no schema specific distributions, and no preview before insert. Those are follow ups.

## Build plan

1. Add the fake data module with types, deterministic generation, and tests, satisfies **AC-2**, **AC-3**, **AC-4**, **AC-6**
2. Add the service generation and insert path with audit and SQLite test, satisfies **AC-5**, **AC-6**
3. Add the Transfer page controls, action, and report, satisfies **AC-1**
4. Verify with a container screenshot, satisfies **AC-7**

## Consequences

**Positive**
- Fast believable data for development and demos.
- Deterministic seeds make bug reports reproducible.
- Uses the existing insert and audit paths, so behavior stays consistent.

**Negative / tradeoffs**
- Values are generic, not schema aware.
- No foreign key awareness, so relational constraints may reject generated rows.
- Masking existing exports is not in this slice.
